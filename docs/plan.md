# sessift 开发计划

sessift 是一个命令行工具：搜索、浏览本机和其他机器上的 AI 编程助手会话记录（Claude Code、Codex、Pi、OpenCode 等）。
多台机器之间**不同步数据**，查询时到各台机器现场查，只把查好的结果传回来。

## 背景：为什么要重写

对 memex 0.31.1 的实测（2026-10-30，本机 MacBook + Mac mini `mm`）：

| 场景 | memex（本机 + mm） | memex（只查本机） |
|---|---|---|
| TUI 打开到出会话列表 | 20.3～21 秒 | 0.6 秒 |
| 搜索 | 1.2～2.1 秒 | 0.1 秒 |
| 会话列表 | 0.9 秒 | 0.2 秒 |

原因：

1. 每个远程请求新开一次 SSH，握手 1.1～1.8 秒；远端 memex 本身只要 0.08 秒。
2. TUI 首页让每台机器传回"最新 1 万条完整记录"再在本地拼会话：本机 293MB，mm 传了 86MB 还没传完，必然超时。
3. 查询线程串行且不可取消，启动时两次查询叠加成两次 10 秒超时。
4. 到 mm 的链路往返约 25ms，但带宽只有 30～180KB/s（流量经过代理），传输字节数决定快慢。

原型验证（一条常驻 SSH 通道，远端现场查、只传结果、zstd 压缩）：

| 请求 | 传输量 | 耗时 |
|---|---|---|
| 首次建通道（一次性） | — | 0.5 秒 |
| 搜索 20 条 | 3KB | 0.10～0.14 秒 |
| 首页 200 个会话 | 22KB | 0.38～0.45 秒 |
| 首页 50 个会话 | 4KB | 0.14～0.19 秒 |

## 设计原则

1. **远端只传结果。** 搜索传前 K 条和截断后的摘要，会话列表传会话摘要，正文按页、按字符预算取。任何响应都有字节上限。
2. **连接常驻。** 本机起一个后台中转进程（broker），对每台机器保持一条 SSH 通道，握手只付一次。命令行每次调用通过 Unix socket 找 broker，单次远程请求的开销约等于一次网络往返。
3. **压缩。** 帧体超过 1KB 就用 zstd 压缩。
4. **并发查询，按截止时间返回。** 本机和各远端同时查；超过截止时间的机器放弃，返回已有结果并给出警告，不会让一台慢机器拖住整体。
5. **请求可取消。** 客户端超时或放弃时通知远端，远端终止对应的查询（包括杀掉后端子进程）。
6. **协议和后端解耦。** 远程协议只描述 sessift 自己的数据模型。过渡期后端调用已安装的 memex，阶段 2 换成自研索引，协议和客户端不用改。
7. **可观测。** `--timing` 输出每台机器的耗时和字节数；`sessift doctor` 逐项诊断连接、版本、延迟。
8. **对异常情况健壮。** 远端 shell 往 stdout 打印杂讯、远端没装 sessift 或版本不对、SSH 断线、broker 进程残留，都要能识别并给出明确提示或自动恢复。

## 阶段 1：远程查询层

### 组件

```
sessift CLI ──(进程内)──> 本机后端（memex 适配器）
     │
     └──(Unix socket)──> broker ──(常驻 SSH 通道, 帧协议 + zstd)──> 远端 `sessift serve --stdio` ──> 远端后端
          （broker 不可用时，CLI 直接起 SSH，带 ControlMaster 复用）
```

- `sessift serve --stdio`：远端服务。从 stdin 读请求帧，并发执行，向 stdout 写响应帧，支持取消。
- `sessift broker`：本机后台中转。按需自动启动，空闲自动退出；版本不一致时自动重启。
- 并发查询与合并：搜索按分数合并，会话按最后活跃时间合并；截止时间到了就返回已有结果。
- 后端接口 `Backend`：`search` / `sessions` / `read` / `context` / `info`。实现：`memex`（过渡）、`fixture`（测试用，可注入延迟）。

协议细节见 [remote-protocol.md](remote-protocol.md)。

### 命令

| 命令 | 作用 |
|---|---|
| `sessift search <query>` | 搜索，支持 `--machine`、`--limit`、`--source`、`--project`、`--cwd`、`--role`、`--session`、`--since`、`--until` |
| `sessift sessions` | 按最后活跃时间列出会话，支持 `--limit`、`--offset` 和过滤项 |
| `sessift read <session-id>` | 分页读会话正文，`--offset`、`--limit`、`--max-chars` |
| `sessift machines` | 列出机器并测连通性、延迟、远端版本 |
| `sessift doctor` | 逐项诊断 |
| `sessift remote install <machine>` | 把本机二进制装到远端（同架构，压缩传输，哈希一致则跳过） |
| `sessift init` | 生成配置，可从 `~/.memex/config.toml` 导入机器 |
| `sessift broker status/stop` | 查看、停止 broker |

输出格式：终端里默认 `text`，管道里默认 `jsonl`，另有 `json`（带警告和各机器耗时的完整结构）。

### 性能目标（本机 ↔ mm 的链路）

| 场景 | 目标 |
|---|---|
| 远程搜索（broker 已连接） | P50 ≤ 200ms |
| 本机 + 远程合并的会话列表（50 条） | P50 ≤ 300ms |
| broker 首次连接 | ≈ 一次 SSH 握手 + 200ms |
| 一台机器无响应 | 截止时间（默认 5 秒）到了返回其余结果 |

过渡期远端每个请求仍要启动一次 memex 进程（约 80ms），阶段 2 换成自研索引后进一步下降。

### 步骤

1. 计划与协议文档。
2. 工程骨架：配置与路径（`SESSIFT_HOME`）、数据模型、输出格式。
3. 协议编解码：帧格式、前导魔数（跳过远端 shell 杂讯）、zstd、帧大小上限。单元测试。
4. 后端：`Backend` 接口、`fixture` 后端、`memex` 适配器（用真实 memex 输出做测试样本）。
5. 远端服务 `serve --stdio`：握手、并发、取消、并发上限、按预算裁剪。集成测试。
6. 客户端连接：SSH / 本地命令两种传输、握手、多路复用、超时、取消、错误提示（远端未安装、版本不符）。
7. 并发查询与合并、CLI 命令、三种输出格式、`--timing`。
8. broker：自动启动、单实例锁、预热、断线重连、空闲退出、版本不一致重启、失败时回退到直连。
9. `machines` / `doctor` / `remote install` / `init`。
10. 在 mm 上端到端验证，和 memex 对比性能。
11. 代码审查、修复、README。

### 测试策略

- 单元测试：编解码、合并、CJK 安全截断、memex 输出解析、配置。
- 集成测试：用"本地命令"传输代替 SSH，`fixture` 后端提供确定数据，覆盖握手、并发、取消、超时、杂讯、远端缺失、多机合并、broker 生命周期。
- 端到端：真实 SSH 到 mm，记录耗时并与 memex 对比。

### 阶段 1 结果（2026-10-30）

全部步骤完成（当时 61 个测试，加上交互界面后共 81 个）。和 memex 0.31.1 对比（本机 + mm，每项 10 次中位数）：

| 场景 | memex | sessift |
|---|---|---|
| 搜索，本机 + 远端 | 2533ms | 154ms |
| 搜索，只查远端 | 2669ms | 193ms |
| 50 个会话，本机 + 远端 | 1080ms | 145ms |
| 搜索，只查本机 | 102ms | 97ms |

计划外补充的可靠性机制：僵死连接探测、途中断线自动重试、broker 退役式替换、终端控制字符清理。

已知限制，留给后续阶段：

- 本机查询仍要启动 memex 进程（约 50～100ms），中文子串搜不到的问题也来自 memex 的分词。阶段 2 的自研索引解决。
- `remote install` 只支持两端同平台。
- 被字符预算截断的正文不能分段续读。

## 阶段 1.5：交互界面（2026-10-30 完成）

### 过程与决定

先做过一版 fzf 前端（`sessift pick` 驱动 fzf，fzf 通过 `--listen` 接收渐进加载的结果）。用户反馈"不是很方便"，要求参考 memex。对比后的差距：fzf 的通用列表可读性差；Enter 要按两次；没有筛选；预览是纯文本；没有会话内阅读和查找；两种模式切换不直观。于是删掉 fzf 版本，用 ratatui 写原生 TUI。

交互照 memex 的焦点模式：搜索框里打字即搜索（停顿 150ms 后发请求），↓ 或 Enter 进入列表，列表里单个字母是命令（Enter/r 恢复、e 放到命令行、Space 速览、Tab 分栏预览、o 全文阅读、s/t/m 筛选、y/Y 复制）。完整按键见 README。

### 结构（`src/tui/`）

| 模块 | 职责 |
|---|---|
| `app.rs` | 状态与按键处理，只产出 `Effect`（要发的请求），不做 I/O，便于单测 |
| `load.rs` | 每个请求一个后台任务，结果用 `Msg` 发回；中止任务即取消远端请求 |
| `view.rs` | 绘制主界面（搜索框、状态行、列表、分栏预览、速览浮层、底部提示）和全文阅读 |
| `md.rs` | 轻量 Markdown（标题、列表、引用、代码块、`code`、**粗体**）、查询词高亮、按显示宽度折行 |
| `theme.rs` | 256 色配色，保留终端背景色 |
| `mod.rs` | 终端进入与恢复（含 panic）、输入线程、事件循环 |

要点：

- 每台机器单独请求，先到先合并；新查询发出时中止旧请求；同一批结果陆续到达时保持选中项不跳。
- 列表请求用 `brief`；选中会话后再查完整信息拿恢复命令。
- 预览：搜索结果用 `context`（命中前 1 条、后 10 条），普通会话取开头 6 条加结尾 12 条；按会话和命中缓存。
- 全文阅读每页 300 条，滚到接近末尾自动加载下一页；从搜索结果打开时一直加载到命中那条并跳过去。
- 画在 /dev/tty 上，stdout 只用来把结果交给 shell 绑定：`run` 或 `edit` 一行，加命令一行。fish/zsh 绑定收到 `run` 时由 shell 执行，命令会进历史；bash 只能放到命令行。
- `sessift` 不带子命令且在终端里时等同 `sessift pick`。

### 验证方式

- 单测：`app.rs` 的状态与按键、`view.rs` 用 ratatui `TestBackend` 渲染、`md.rs` 的排版与折行。
- 端到端：在伪终端里起交互式 fish，按 Alt-M、输入、按 `e`/Enter 检查命令行（用 Python + pyte 截屏）。注意 pyte 不支持备用屏幕，且宽字符被半覆盖时不清另一半，截图里少空格、列错位、残影都是模拟器的问题，不代表真实终端。

### 后来的改进（2026-10-31）

- 搜索框里按字母是打字，原来要先进列表才能用 s/t/m/a 筛选，容易困惑。改成 Alt 加同一个字母在任何焦点下都能切换筛选；状态行的按键提示跟着焦点变（搜索框里显示 `Alt-s`，列表里显示 `s`），底部提示也写明。
- 鼠标：单击选中、双击恢复（原来是再点一次已选中的会话就恢复，容易误触）；滚轮按鼠标位置滚列表或预览；状态行的筛选单击弹出下拉菜单；底部提示和速览浮层的提示可点；单击搜索框定位光标；点速览浮层外面关闭。
- 实现：`view` 每次绘制把各区域、筛选、可点提示、菜单项的位置记进 `App::regions`，`app` 按位置处理鼠标事件；可点的提示直接按它的键，复用键盘逻辑。

### 和 memex 相比还没做的

- 首页顶部的活动图表（会话数或 token）。
- 按项目筛选的下拉菜单（目前靠搜索词）。
- 分享会话。

## 阶段 2：自研索引（2026-10-30 完成）

### 目标与结果

本机全量数据（9.7GB，2607 个文件，47.2 万条记录）上的实测：

| 目标 | 结果 |
|---|---|
| 去掉对 memex 的依赖 | 默认后端改为 `native`；对比完成后 memex 适配器已删除（2026-10-31） |
| 中文词在句中可搜（"回滚"命中"在那之前回滚还来得及"） | 四种来源的样本都有这条验收用例 |
| 本机查询 P50 < 30ms | 命令行从启动到结束 22～25ms（含进程启动约 5ms、增量检查约 12ms）；常驻进程（TUI、远端服务）里每次查询约 5～10ms。memex 同一查询 109ms。有会话正在写入时要先增量更新，起初 90～140ms，切换时修复为 25～35ms（见下文） |
| 会话列表 < 10ms | 进程内约 5ms；命令行总计 22ms |
| 无变化时的增量检查 < 50ms | 12ms（并行遍历目录 5ms、比对 2ms、读文件表 3ms） |
| 冷建全量 < 2 分钟 | 12.9 秒，峰值内存 760MB |
| 索引 < 1GB | 482MB（memex 5GB） |

mm 上（957MB，209 个文件）冷建 0.93 秒，0 行解析错误，搜索约 10ms。

### 结构（`src/index/`）

| 模块 | 职责 |
|---|---|
| `tokenizer.rs` | 中英文混合分词：字母数字连续段转小写，纯 ASCII 词做英文词干；汉字、假名、韩文切成重叠的两字词，单字保留 |
| `source/` | 各来源解析器和公共驱动。JSONL 来源实现 `JsonlFormat`（逐行，可从字节偏移续解析）；OpenCode 读 SQLite |
| `store.rs` | SQLite：`files`（增量状态）、`sessions`、`records`（每条记录在原文件里的位置） |
| `fulltext.rs` | Tantivy：每条记录一个文档；按角色加权的打分；"每个会话只取最好一条"的收集器；段合并策略（查询里只合并小段） |
| `directory.rs` | Tantivy 的文件目录：同 `MmapDirectory`，但同步用普通 `fsync` |
| `ingest.rs` | 增量入库：发现文件、对比、并行解析、单线程写入；写锁；大量待处理时交给后台进程 |
| `query.rs` | 查询：查询前按需刷新（最多每 2 秒一次），搜索、会话列表、分页阅读、上下文 |
| `reader.rs` | 按位置读回原文，`.zst` 流式解压 |
| `project.rs` | 从 cwd 找 git 仓库根目录（worktree 归到主仓库）作项目名 |

格式要点见 [formats.md](formats.md)。

### 与原方案不同的决定

- **搜索摘要存了一份压缩文本。** 起初完全不存正文，摘要从原文件读。实测命中大多落在 Codex 的 `.zst` 旧会话里，每条摘要都要从头解压到命中位置，一次搜索要 130～160ms。现在把已索引的那段文本（每条消息最多 64KB、工具调用和输出最多 8KB）用 zstd 存进 Tantivy，摘要直接取，搜索降到 25ms，索引从 278MB 增加到 482MB。分页阅读和上下文仍然读原文件，内容完整，不截断。
- **原文件被删掉的会话从索引里移除，不标记保留。** 既然不存完整正文，留下的条目也读不了。memex 里那些原文件已删除的会话（本机有 334 个 Claude 会话、83 个 omp 会话）不导入。Claude Code 默认会删除 30 天前的记录（`cleanupPeriodDays`），想长期保留需要调大这个设置。
- **会话 = 一个文件。** Codex 少数会话分成多个文件（本机 11 个），目前分别列出，没有合并。
- **record_id 用原文件位置**（`<会话键>-<字节偏移>-<行内序号>`），不用原生事件 id。它对所有来源都适用，能直接定位，而且 Codex 文件压缩后不变。
- **首次建索引交给后台。** 查询发现待处理超过 256MB 时，在后台起 `sessift index`，自己先用已有的索引回答；如果还从没建成过，提示稍后再试。
- **索引文件用普通 `fsync`，不强制落盘。** 见下文"切换后发现的问题"。

### 测试

- 每个来源都有虚构样本（`tests/fixtures/home/`，布局和真实的 HOME 一致）。Claude 和 Codex 的解析结果逐条与调研时写的 Python 参考实现核对（`tests/fixtures/expected/`）。
- 解析器的约定（一行产生的记录只取决于这一行）对每个样本都检查：整文件解析，再逐行读回，比对文字。
- `tests/native.rs`：增量追加、原地改写、删除、Codex 压缩改名、OpenCode 数据库变化、重建。
- `tests/cli.rs` 里的 `native_backend_end_to_end`：真实二进制、两台机器（远端用本地命令代替 SSH），四种来源都能搜到"回滚"。

### 切换到 native（2026-10-31）

本机改配置为 `kind = "native"`，`sessift index` 冷建 12.9 秒；`sessift remote install mm` 后 mm 首次查询在后台建索引，约 1 秒。

#### 切换后发现的问题

- **有新记录时，查询前的增量更新要 90～140ms。** 只要有一个会话正在进行（用 sessift 时几乎总是这样），每次命令行查询都要付这个代价，和 memex 一样慢。原因：Tantivy 每写完一个文件调用 `sync_data()`，Rust 在 macOS 上把它实现成 `F_FULLFSYNC`（等磁盘把缓存写进介质），实测每次约 5ms，一次提交要同步十几个文件。普通 `fsync` 只要 0.03ms。改法：`src/index/directory.rs` 包一层 `MmapDirectory`，写文件和 `meta.json` 时只用普通 `fsync`。索引可以从原文件重建，扛得住进程和内核崩溃就够了，断电不值得这个代价（SQLite 这边本来就是 WAL + `synchronous=NORMAL`）。之后增量更新 25～35ms。
- **偶尔一次查询要 1 秒以上。** Tantivy 默认的 `LogMergePolicy` 在某次提交后，会把攒够 8 个、每个一两万条的段合成一个，重写约四分之一的索引，而查询前的刷新会等合并完成。改法：查询里的刷新只合并小段（每段不到 2000 条、攒够 8 个，最多 1.6 万条），默认策略要做的大合并交给 `sessift index`。查询发现有大合并待做时，在后台起 `sessift index`（和首次建索引同一套机制）；`sessift index` 没有新内容时也会做待做的合并。
- **没有任何会话记录的机器一直提示"索引正在建立"。** 没有文件要解析时直接返回，从没写过 `refreshed_ms`。现在第一次一定走完整流程，建一个空索引。

#### 和 memex 的对比

延迟见 README（20 次取中位数）：本机 + 远端搜索 31ms 对 2171ms，只查本机 22ms 对 87ms，50 个会话 31ms 对 624ms。

会话集合（本机）：两边都有的是 Claude 259、Codex 358、OpenCode 47、Pi 355 个。差异全部能解释：

| 只有 memex 有 | 数量 | 原因 |
|---|---|---|
| 原文件已删除 | Claude 334、omp 83、Pi 1；mm 上抽查到的 86 个也是 | memex 保留了正文副本；sessift 按设计不保留 |
| `~/.codex/history.jsonl` 里的输入历史 | 约 120 | memex 把输入历史当成会话，对应的会话文件大多已删除 |
| sessift 不支持的来源 | Grok 11、Cursor 1、Antigravity 1、OpenClaw 1 | 见"留给阶段 3" |
| 空会话 | 2 | 一个只有头部的 `codex exec`；一个没有新消息的 Claude fork（内容全在父会话里） |

只有 sessift 有的：约 1550 个 Codex 会话（主会话 690 个，其余是子 agent、guardian、exec、fork），全部是压缩过的 `.jsonl.zst`，时间从 2025-10 到 2026-10。memex 不读压缩文件，它列出的 Codex 会话都是最近一个月的。

搜索结果（23 个固定查询，中英文各半，本机和 mm 各取 memex 的前 10 个会话，共 448 个）：其中 218 个 sessift 没有（上表的原因）；其余 230 个里 sessift 能搜到 214 个（93%），其中 79 个也在 sessift 的前 10。剩下 16 个都是有意的差别：

- 多个词的查询，memex 是任一出现即可（"cargo test" 命中只有 cargo 的记录），sessift 要求同一条记录里都出现。
- 系统注入的文字（团队、权限说明）和本地命令的输出，sessift 不索引。
- fork 会话里复制来的历史，sessift 只算在父会话名下。

前 10 的重合度低，一部分是因为 sessift 多了一年的 Codex 会话参与排序，另一部分是打分方式不同（按角色加权）。哪边排得更好需要人工判断，留到阶段 3。

memex 适配器（`src/backend/memex.rs` 和它的测试）已删除；配置里还写着 `kind = "memex"` 时会报错并提示改成 `native`。随后两台机器都卸载了 memex 和它的 herdr 插件（`Ctrl-B m`），会话搜索只用 sessift。`scripts/bench.py` 在装了 memex 的机器上仍会同时测它作对照。

### 留给阶段 3

1. 排序：前 10 和 memex 重合度低，用一组固定查询人工评判；列表默认是否隐藏 Codex 的 guardian、exec 线程。
2. 更多来源：Grok（本机 17 个会话，37MB）优先，Cursor、Antigravity、OpenClaw 各只有一个，暂不做。
3. Codex 多文件会话合并；没有新消息的 Claude fork 是否在列表里单独显示（能恢复，但搜索命中都算在父会话）。
4. 按输入前缀搜索（边打字边搜时，没打完的词也能匹配）。

### 原方案（实施前）

以下是开工前的设计，保留作对照。

#### 目标

- 去掉对 memex 的依赖。本机查询不再每次启动 memex 进程（约 50～100ms），在进程内直接查索引，目标 P50 < 30ms；会话列表 < 10ms。
- 中文词在句子中间也能搜到。验收用例：一条助手消息"在那之前回滚还来得及"，搜"回滚"必须命中（memex 的英文分词搜不到）。做成固定的测试样本。
- 不复制会话原文，索引体积 < 1GB（memex 是 5GB，其中 4.2GB 是原文副本）。
- 增量刷新：没有变化时 < 50ms；冷建全量（本机约 10GB 原始数据）< 2 分钟。

#### 数据来源（本机实测规模）

| 来源 | 位置 | 规模 | 优先级 |
|---|---|---|---|
| Codex | `~/.codex/sessions`、`~/.codex/archived_sessions`（rollout JSONL） | 5.6GB + 0.3GB，约 360 个文件 | 1 |
| Claude Code | `~/.claude/projects/*/*.jsonl` | 2.3GB | 1 |
| Pi / Oh My Pi | `~/.pi`、`~/.omp/agent/sessions` | 1.5GB | 2 |
| OpenCode | `~/.local/share/opencode` | 92MB | 3 |

格式参考 memex 的解析器（github.com/nicosuave/memex 的 `src/sources/{claude,codex,pi,opencode}.rs`），但自己实现；先在本机抽样真实文件，整理出脱敏的测试样本。

#### 存储设计（`~/.sessift/index/`）

- `sessions.sqlite`：
  - `sessions`：source、session_id、source_path、project、cwd、title、started_ms、last_ms、message_count、kind（主会话或子 agent）、parent_session。
  - `files`：path、inode、size、mtime、已解析到的字节偏移、解析器版本，用来做增量。
- Tantivy 索引，每条记录一个文档：
  - 存：record_id、session 引用、role、tool_name、ts（fast field），以及原文位置（文件 id + 字节偏移 + 长度）。
  - 只索引不存：正文。工具输出只索引前 8KB 左右，控制体积。
  - 摘要、预览、全文阅读都按位置从原文件读（pread 或 mmap）。原文件被删掉的会话，在列表里标出来。
- record_id 要稳定：用原生事件 id，没有的话用"文件路径 + 字节偏移"的哈希。

#### 中英文混合分词

- 自定义 Tantivy tokenizer：字母和数字连续段转小写成词（英文可选轻量词干）；汉字、假名、韩文连续段切成重叠的两字词（bigram），只有一个字时保留单字。
- 查询用同一个分词器：中文词变成 bigram 的短语查询（带位置），这样"回滚"能命中"在那之前回滚还来得及"；单字查询用前缀匹配。
- 评分用 BM25；在 Codex 上验证工具输出噪音对排序的影响，必要时按 role 加权（用户和助手消息高于工具输出）。

#### 解析与增量

- 每个来源一个解析器，输出：会话元数据，以及带字节偏移的记录（user、assistant、tool_use、tool_result）。
- JSONL 是追加写：只解析上次偏移之后的新内容；文件变小或 inode 变了就整文件重建。
- 标题：取第一条真正的用户消息，跳过 `/clear` 之类的命令、system reminder、`<command-name>` 等，截到 80 字。
- 项目名：从 cwd 往上找 git 仓库根目录，取目录名并缓存；找不到用 cwd 的最后一段。
- 恢复命令按来源生成，比如 Claude `cd '<cwd>' && claude --resume <id>`、Codex `codex resume <id>`。Pi、OpenCode 的写法要在本机核实。
- 刷新时机：查询前检查是否过期（目录 mtime 加文件 stat，代价很低）；`sessift index` 手动全量或增量。文件监听（FSEvents）留到阶段 4。
- 解析并行（rayon），写入单线程，批量提交。

#### 接入

- `Backend::Native` 实现现有接口（search、sessions、read、context、info），配置 `backend.kind = "native"`。协议和 TUI 都不用改。
- 保留 memex 后端用于对比；新增 `sessift index [--rebuild]` 和 `sessift index stats`。
- 本机和 mm 都切到 native 之后，用 `scripts/bench.py` 和一组固定查询，对比 memex 的结果集和延迟。

#### 步骤

1. 抽样本机四种来源的真实文件，整理格式要点和边界情况，做脱敏样本。
2. 记录模型、位置方案、分词器（先写测试，含"回滚"用例）。
3. Claude 和 Codex 解析器，含增量。
4. SQLite 表、Tantivy schema、入库流水线。
5. Native 后端的各个操作，摘要从原文读取。
6. Pi / omp、OpenCode。
7. `sessift index`，查询前自动刷新。
8. 两台机器切换到 native，做性能和召回对比，更新文档。

## 阶段 3：搜索质量（方案，2026-10-31）

### 现状（本机实测）

| 问题 | 数据 |

### 目标

1. 一套能反复跑的评测，每次改排序都跑，用数字决定留不留。
2. 会话列表默认只列人的对话；自动线程一键可见。
3. 评测指标提升，guardian、exec 不再压过主会话。
4. 支持 Grok。
5. 交互界面边打字边搜：没打完的英文词也能匹配。
6. 延迟不退化：只查本机的搜索，命令行 P50 仍 < 30ms。

### 步骤

#### 1. 评测集和评测脚本

- 评测数据含真实会话内容，放 `~/.sessift/eval/`，不进仓库；仓库里只有脚本 `scripts/eval.py` 和虚构样本上的单测。
- 两类查询：
  - **找回某个会话**（约 60 条）：从本机和 mm 的主会话里按来源、时间分层抽样，根据会话中间的内容（不只看标题）写 1～3 个词的查询，模拟凭印象找会话，中英文都有，标注目标会话。指标：MRR@10、前 10 命中率。
  - **主题查询**（约 20 条，部署、rollback、tantivy 这类）：前 10 个结果标注相关与否。指标：P@10，另外统计前 10 里 guardian、exec 的个数。
- 先由 Claude 读会话起草查询和标注，用户抽查；用户自己真实搜过的词可以随时加进文件。
- 脚本经 `sessift search --format jsonl` 调用，所以本机、远端都能测；同时记延迟。输出和上一次结果的对比。

#### 2. 会话种类和列表默认

- `Filters` 加 `kinds`（新字段，`serde(default)`；旧版远端会忽略它、照常返回全部）。
- 会话列表默认只列 `main`、`fork`、`background`，且至少有一条消息（顺带解决没有新消息的 Claude fork）。`subagent`、`guardian`、`exec` 默认不列：子 agent 恢复的本来就是父会话。
- 命令行 `--kind exec`（可重复）或 `--all-kinds`；交互界面加一个键在"对话 / 全部"之间切换，状态行显示当前选择。
- 搜索不隐藏，靠第 3 步的权重压低。
- Codex 多文件会话（本机 10 个）在列表和"每会话一条"的搜索里按 `source + session_id` 合并成一行；阅读时按文件顺序接起来读。

#### 3. 排序

每项单独实现、单独评测，只保留让指标变好的：

- **会话种类权重**：guardian、exec、subagent 打折（初值 0.3、0.6、0.8，按评测调）。
- **会话级聚合**：会话分数 = 最好的一条 + 其余命中条数的对数加成。反复讨论某件事的会话比偶然提到一次的更可能是要找的。
- **跨记录的多词匹配**：全部词在同一条记录里出现的排前面；其次全部词出现在同一会话的不同记录里，分数打折。
- **标题**：命中会话标题的加分（对前几百个候选会话在查询后计算，不改索引）。
- **时间**：轻微的新近加成，只在分数接近时起作用。

#### 4. Grok 来源（`src/index/source/grok.rs`）

- 位置：`$GROK_HOME` 或 `~/.grok` 下的 `sessions/<URL 编码的 cwd>/<会话 id>/chat_history.jsonl`，元数据（cwd、创建和最后活跃时间、标题）从同目录的 `summary.json` 取。
- 记录：`user` 的文字（带 `synthetic_reason` 的是注入内容，跳过）；`assistant` 的 `content` 和每个 `tool_calls`；`tool_result`（图片跳过）；`backend_tool_call`（服务端的搜索）当工具调用。`system`、`reasoning` 跳过。
- 对话记录里没有逐条时间，从 `updates.jsonl` 按轮次补，补不到就用会话的时间。
- 增量：只追加时从偏移续解析，被改写（压缩上下文）时整文件重解析，和 Claude 一样用指纹判断。
- 恢复：`cd '<cwd>' && grok --resume <id>`。
- 虚构样本，`docs/formats.md` 加一节。

#### 5. 边打字边搜

- `SearchRequest` 加 `prefix`（`serde(default)`）：最后一个英文词按前缀匹配，至少 2 个字母，最多扩展到 64 个词，避免很短的前缀拖慢查询。前缀同时按原样和词干形式匹配（索引里存的是词干）。
- 交互界面的请求带 `prefix`，命令行不带。旧版远端忽略它，退化为整词匹配。
- 中文不需要：单字已经按包含匹配，两个字以上本来就是完整的二元词。

#### 6. 向量检索：评测之后再定

第 3 步做完后看"找回某个会话"里剩下的失败：如果主要是换了说法（查询里的词在会话里根本没出现），再考虑本地多语言向量模型，只对用户和助手消息（约 8 万条）建向量，和 BM25 按名次融合（RRF）；否则不做。

#### 7. 收尾

两台机器更新、`scripts/bench.py` 确认延迟、README 和 `docs/formats.md`、本节补上结果。

### 阶段 3 结果（2026-10-31）

第 1～5 步和收尾完成，两台机器已更新。向量检索（第 6 步）待用户决定，见下文。

#### 评测集

- 从本机主会话按来源、时间分层抽 60 个（Claude 16、Codex 22、Pi 16、OpenCode 6），由三个 agent 各读 20 个会话、在不看搜索结果的情况下写查询：69 条普通查询 + 7 条故意换了说法的（查询词在会话里没有出现），3 个会话因为是纯自动化内容被跳过。另有 22 个主题查询。
- 只评测本机：排序参数靠 `SESSIFT_RANK` 切换，只对进程内查询生效。
- 写查询的会话和它的子 agent 会话里有目标会话的原文，评测时排除（`exclude.txt`）。以后在 Claude 里做评测相关的工作，要把那个会话也加进去。

#### 排序

| | MRR@10 | 第一名 | 前 10 | 换说法的查询前 10 | 主题查询前 10 里的 guardian/exec |
|---|---|---|---|---|---|
| 阶段 2 | 0.815 | 48/69 | 66/69 | 0/7 | 16 |
| 按会话打分（默认参数） | 0.891 | 55 | 69 | 0 | 0 |
| 再加解析清理 | 0.898 | 56 | 69 | 0 | 0 |

逐项去掉的影响（MRR@10）：跨记录匹配 -0.044（另外 3 条查询完全找不到），会话种类权重、命中条数、标题、新近各约 -0.01（每项约一条查询从第二名掉回）。参数没有按评测细调：69 条查询里 0.008 就是一条查询的名次变化，在默认值附近试过的其他取值（跨记录 0.3～0.7、标题 0.15～0.5、子 agent 0.6～1）都不比默认好，说明不是调出来的峰值。

没进第一名的 13 条，排在前面的大多是同一件事的另一个会话（同一个问题先后问了两次、同一项目的前后几次），关键词排序已经接近上限。

试过、没有留下的：缺一个词也算命中（三个词以上的查询缺一个时打折计分），对换说法的查询没有帮助。

#### 其他改动

- **会话列表**默认只列对话（`main`、`fork`、`background` 且至少一条消息）；`--kind`、交互界面 `a` 键切换。按会话 ID 查找和搜索不受影响。本机最近 50 个会话里原来 23 个是 `codex exec`。
- **Codex 多文件会话**合并成一行，阅读时按文件顺序接起来。
- **边打字边搜**：最后一个英文词按前缀匹配，扩展词分数打五折，所以打完的词排序不变（评测 MRR 相同）。两个字母的前缀约 40ms，其余 20～30ms。
- **解析清理**（各 agent 读会话时发现的注入文字）：Codex 的目标续写提示、IDE 和附件包装、记忆引用；Pi 贴进来的 skill 文件。
- **Grok**：本机 11 个会话、mm 2 个，0 行解析错误。`summary.json` 里的标题比对话记录晚写，所以它的修改时间也算作会话变化；逐条时间从 `updates.jsonl` 按轮次补；压缩上下文后的摘要作为助手记录索引（压缩前的历史在文件里已经没有了）；`grok -p` 归为 `exec`。
- **阅读的字符预算**：以前预算用完后剩下的记录变成空文字，`next_offset` 却是空，看起来像读完了（写评测查询的 agent 都踩到了）。现在这一页到此为止，`next_offset` 指向下一条。
- 延迟（`scripts/bench.py`，20 次中位数）：本机 + 远端搜索 29ms，只查本机 21ms，50 个会话 30ms，和阶段 2 持平。冷建全量 8.8 秒（原来 12.9 秒），索引 462MB。

#### 向量检索：待定

## 阶段 5：herdr 插件与 agent skill（2026-10-31）

### Alt-M 在 herdr 里没反应

不是代码问题：fish 的绑定在 `fish_user_key_bindings` 里，只对之后启动的 shell 生效，而 herdr 的 pane 会活好几天，加绑定之前开的 shell 没有它，`exec fish` 一次就好。另外 agent pane 里按 Alt-M，按键被 agent 收走，到不了 shell。所以 shell 命令行继续用 Alt-M，herdr 里另给一个在任何 pane 都能用的入口。

### herdr 插件（`herdr/`）

- 安装 `herdr plugin install kadaliao/sessift/herdr`，绑 `prefix+m` 到 `sessift.open`（memex 插件原来用这个键）。
- `open` action 打开 popup 类型的插件 pane，里面跑 `picker.sh`：找 sessift（PATH、`~/.local/bin`、Homebrew、`~/.sessift/bin`），执行 `sessift pick --herdr`；找不到、版本太旧或出错时停住等回车，免得浮层一闪而过。
- `sessift pick --herdr`（`src/herdr.rs`）选中后不输出命令，自己调 herdr 的命令行：
  - Enter：本机会话先在 `pane list` 里找 `agent_session` 等于这个会话 ID 的 pane，有就 `agent focus` 过去，免得同一个会话恢复两份；否则看浮层下面的 pane（`HERDR_PLUGIN_CONTEXT_JSON` 的 `focused_pane_id`，popup 自己没有 `HERDR_PANE_ID`），它的前台进程就是 pane 自己的 shell 时在这里 `pane run`，命令进 shell 历史；都不是就在当前 workspace `tab create`（本机会话设好 cwd，标题用会话标题，远端加机器名前缀）再 `pane run`。
  - e：浮层下面是空闲 shell 就 `pane send-text` 放到命令行；否则复制并弹 herdr 通知。
  - herdr 调用失败时复制恢复命令、用通知显示错误：浮层关掉后 stderr 就看不到了。
  - 命令按 `$SHELL` 转义（新 tab 和浮层下面的 pane 跑的都是登录 shell）。
- "空闲 shell"的判断：前台进程组等于 pane 的 shell 进程，并且进程名是已知的 shell。只看前者不够：直接以命令启动的 pane（插件 pane、`type = "pane"` 的命令）里，那个命令本身就是"shell"。
- 测试：`src/herdr.rs` 用假的 herdr 脚本（记录参数、返回预设 JSON）覆盖各分支；在真实 herdr 里用 fixture 后端的假会话（恢复命令是 `echo`）在两个后台 tab 里跑过四条路径。
